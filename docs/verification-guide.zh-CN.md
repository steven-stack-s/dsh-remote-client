# 图形环境验证指南（Windows）

[English](verification-guide.md) | [简体中文](verification-guide.zh-CN.md)

本指南用于在 **Windows** 上验证 dsh-remote-client（当前已发布版本：**0.2.5**）。

本开发环境是无 GUI 的 Linux 容器，因此下列内容**无法在此验证**：窗口外观、菜单与托盘的实际呈现、登录态持久化、离线重连行为等。这份指南就是为把它们逐项验证出来而写的。

> ✅ **已由真机确认**：客户端能连上 dsh（走「本地地址 + 带 `?token=` 的完整 URL」，即 launch token 握手）。
> 下面各项仍需你确认。

> 📖 **版本历史**：各版本「改了什么、为什么改」见仓库根目录的 `CHANGELOG.md`。本指南中凡标注「0.2.x 新增 / 修复」的验收项，都能在那里找到对应的条目。

> 📌 **Windows 提示**：实现最初按 macOS/Linux 习惯写，识别出环境是 Windows 后已追加修复若干会立刻暴露的问题（托盘空图标可能不显示、关窗即退出与所选能力冲突等）。**请以最新构建的安装包为准。**

## 0. 准备

### 0.0 最快路径：直接用安装包（推荐）

**如果你只想验证"客户端能不能用"，不需要装任何开发环境** —— 安装包已构建完成：

```
release/DSH.Remote.Client-<版本>-setup.exe   （约 106MB，自带 Electron 运行时）
```

`<版本>` 就是你拿到的那一份的版本号（见文件名或 Release 标题）——**这里刻意
不写死具体值**，理由与下面不写死 SHA256 相同：它每次发版都会变，而写死的值
必然在某个版本之后变成错的（上一版就漏改过一次：文档里留着 0.1.0 的哈希，
而发布的已经是 0.1.1）。

包的正确性用 **SHA256 核对**：值在对应的 GitHub Release 说明里（CI 构建时会打印）。
刻意不把哈希写死在这里——它是**跟着每个构建变**的，写死就必然会过期，
而过期的哈希比没有哈希更糟（会让人以为下错了包）。

> **产物名从 v0.1.8 起固定为 `DSH.Remote.Client-<版本>-setup.exe`**（点号分隔、
> 不含空格），本地构建与 Release 上的名字**完全一致**。
>
> v0.1.7 及更早不是这样：那时的 `artifactName` 用了 `${productName}`，而
> `productName` 含空格，于是同一个包在三个地方有三个名字（磁盘上带空格、
> `latest.yml` 里是连字符、GitHub 附件是点号）。这直接导致 v0.1.7 的自动更新
> 下载 404——更新器按 `latest.yml` 里的名字去找，Release 里却只有点号那个。
> 详见 `electron-builder.yml` 里 `artifactName` 上方的注释。

双击安装（不需要管理员权限），然后直接跳到 §1。

> ⚠️ 未做代码签名，SmartScreen 会提示「未知发布者」→ 点「更多信息」→「仍要运行」。

## 1. 关键起点：优先用 `127.0.0.1` 验证，可零配置

**如果 dsh-docker 就跑在这台 Windows 上**（Docker Desktop / WSL2），用 `http://127.0.0.1:3080` 添加主机——这是最省事的路径，能一次绕开两个坑：

| 坑 | 用 127.0.0.1 时 |
|---|---|
| dsh 的 trust fence 拒绝非 loopback Host（页面能开但 `/api` 全 403） | `127.0.0.1` 是 loopback，**直接放行** —— 不用配 `DSH_TRUSTED_HOSTS`，不用装 `dsh-remote` |
| 明文 HTTP 非安全上下文（剪贴板失效） | `127.0.0.1` 是浏览器认定的可信源，**是安全上下文**，剪贴板正常 |

只有当你需要用**局域网 IP 或域名**访问时，才需要处理这两件事（见 §9）。

> Docker Desktop 默认会把容器端口映射到 Windows 的 `localhost`，所以这条路径开箱即用。

## 2. 起步：最小闭环（最高优先级）

```powershell
pnpm dev
```

**预期**：出现一个标题为「添加 dsh 主机」的窗口（560×420），含地址、显示名两个输入框和「添加并打开」按钮。

**这一步验证的是阶段 1 修的两个 P0**：
- `out/renderer/` 此前根本不生成 → **首启白屏**
- preload 此前内联了整个 npm `electron` 包 → `window.shell` 为 `undefined` → **按钮点了没反应**

**若白屏**：在窗口里按 `Ctrl+Shift+I` 开 DevTools 看 Console。`pnpm dev` 的终端也会打印主进程错误。

**若按钮无反应**：DevTools Console 里敲 `window.shell`，是 `undefined` 就是 preload 加载失败。

## 3. 核心验证：连上一台真实 dsh

在欢迎页填入地址并提交。

**预期（按顺序）**：
1. 提交后立即打开主机窗口，标题先是主机显示名；
2. **远端在线** → 出现 dsh 界面或登录页（取决于是否装了 `dsh-remote`）；
3. **远端不可达** → 壳自有的离线页，给出失败原因 + `DSH_TRUSTED_HOSTS` 提示。

**然后逐项确认**：

| 项 | 操作 | 预期 |
|---|---|---|
| 登录态持久化 | 登录 → **托盘 →「关闭客户端」**（不是关窗）→ 重新启动客户端 | 直接进入已登录状态 |
| 多主机隔离 | 添加第二台（可用不存在的地址）→ 从**托盘「主机列表」**切回第一台 | 两台登录态互不影响 |
| 托盘 | 看任务栏右下角（可能需要点「显示隐藏的图标」的 `^`） | 有**鲸鱼**图标；右键菜单含「打开客户端 / 主机列表 / 添加主机… / 编辑主机… / 客户端设置 / 关闭客户端」 |
| 主机切换 | 托盘「主机列表」→ 点另一台 | 窗口切到该主机 |
| 编辑主机 | 托盘 →「编辑主机…」，或按 `Ctrl+E` | 窗口顶部可**下拉选择任意一台**主机（不必先切到它）；改显示名 / 地址 / 令牌后保存生效 |
| 重置登录态 | 托盘「主机列表」→ 某台 →「重置登录态」→ 重开该主机 | 回到登录页 |
| 删除 | 托盘「主机列表」→ 某台 →「删除…」 | 弹出确认框（默认按钮是「取消」，**误按回车不会删**）；删除后菜单不再列出 |
| **顶部跟随主题** | 在 dsh 设置里**换一套皮肤**（如深色 ↔ 浅色） | 窗口最上面那一条（dsh 自绘的标题栏）**跟着变色**，与页面皮肤同色；系统的最小化/最大化/关闭按钮仍可用、图标清晰可见 |
| 刷新页面 | 在 dsh 窗口按 `Ctrl+R` | 页面重新加载（重新请求主机 origin，等同托盘「重新加载」） |
| DevTools | 在 dsh 窗口按 `Ctrl+Shift+I` 或 `F12` | 打开开发者工具（诊断用，也是 DOM 勘察脚本的入口） |
| 拖拽上传 | 拖一个本地文件进 dsh 窗口 | 作为附件进远端工作区（前端自带能力，壳未处理） |

> ⚠️ **「打开」不等于「刷新」**
>
> 对**当前已打开**的主机，选「打开」只会把窗口拿到前台（`show()` + `focus()`），**不会重新加载页面** —— 这是刻意设计，避免同一地址并存两份 WebSocket。
>
> **需要重新加载页面时，请用「主机列表」→ 该主机 →「重新加载」，或按 `Ctrl+R`。**

### 3.00 界面构成：Windows 上主机管理在托盘

> **本文以下所有「托盘 → …」「主机 → …」的入口，在 macOS / Linux 上同样存在于菜单栏里**（那些平台仍是有边框窗口，菜单栏照常显示）。Windows 请一律走托盘。

**Windows 上的窗口**（本节重点，因为它与其它平台不同）：

```
┌────────────────────────────────────────────┬──────────────┐
│  （dsh 自绘的标题栏：跟随应用主题、可拖拽）  │  ─  □  ✕     │  ← 系统窗口按钮画在这条右侧
├────────────────────────────────────────────┴──────────────┤
│                       dsh 页面                             │
└────────────────────────────────────────────────────────────┘
```

- 窗口是**无边框**的：系统标题栏被去掉，顶上那一条由 dsh 自己画，因此**会跟着换肤插件一起变色**。
- **原生菜单栏不显示**（Electron 对 frameless 的定义就是 no chrome，chrome 明确包含 toolbars）。它的快捷键仍然有效（`Ctrl+N` 添加主机、`Ctrl+E` 编辑主机、`Ctrl+Q` 退出），但**看不见**——菜单栏一隐藏，这些键就没有任何提示面了。
- 因为菜单栏没了，**主机管理全部在托盘里**（下一节）。

**系统托盘**（任务栏右下角，可能需点 `^` 展开隐藏图标）—— 主机管理与开关都在这里：

```
打开客户端     ← 唤起窗口（已隐藏则唤回；已销毁则按当前主机重开）
──────────────
主机列表 ▸          ← 每台主机一个子菜单：打开 / 新窗口打开 / 重新加载 / 立即重试 / 重置登录态 / 删除…
添加主机…       ← Ctrl+N
编辑主机…       ← Ctrl+E（窗口内可下拉切换到任意一台）
──────────────
客户端设置      ← Ctrl+,（0.2.0 起；托盘里叫「客户端设置」而不是「设置…」，见下）
──────────────
关闭客户端     ← 真正退出（点窗口的 ✕ 只是隐藏，不会退出）
```

> **托盘这一项为什么叫「客户端设置」**：它紧挨着的「添加主机…」「编辑主机…」都作用于**主机**，不写清对象会让人以为这也是主机维度的设置。菜单栏里那份仍叫「设置…」（那里只有它一个，没有歧义）。

> **为什么托盘又把主机管理收回来了**：托盘曾经只有「打开客户端 / 关闭客户端」两项，理由是主机管理**已经全部在菜单栏里**、而托盘是历史上最不可靠的一环。这个理由在当时成立，但现在**前提没了**：Windows 上窗口改成无边框后菜单栏不再显示，而「编辑主机…」「删除主机…」**没有快捷键**——不搬回托盘就等于彻底失去入口。
>
> **图标随系统主题变色**：浅色主题用**黑鲸鱼**、深色主题用**白鲸鱼**、离线重试中用**灰色**（离线优先于主题）。
>
> **菜单会跟着配置重建**：增删主机、切换当前主机、离线状态变化后，托盘菜单都会立刻反映最新状态，不会停在旧列表上。

**如果托盘不出现**，请从**命令行**启动客户端以捕获日志（会明确打印失败原因，不再是静默失败）：

```powershell
& "$env:LOCALAPPDATA\Programs\DSH Remote Client\DSH Remote Client.exe"
```

留意是否有 `[dsh-remote-client] 托盘创建失败…` 或 `启动流程失败…`。
**Windows 上托盘不可用 = 主机管理没有入口**（菜单栏已经不显示了），因此这一项在 Windows 上比以往更关键；若确实失败，请先按上一行从命令行启动取证，再用 `Ctrl+N` 临时添加主机。

> 补充：若托盘**装配失败**，应用会退回「关掉所有窗口即退出」的行为。这是刻意的 —— 否则应用会变成一个既看不见、也无法退出的幽灵进程。

### 3.000 未装认证插件的 dsh：必须粘贴带 token 的完整地址

如果你的 dsh **没有装** `@xgone/dsh-remote` 之类的认证插件，它会启用 dsh 原生的 **launch token** 保护：
直接访问地址会返回 `401 dsh web authentication required; reopen the URL printed by dsh web.`

**正确做法**：把 `dsh web` 启动时**打印的那一整行 URL** 原样粘进「添加主机…」：

```
http://127.0.0.1:3080/?token=xxxxxxxxxxxxxxxx
```

客户端会自己把它拆成 origin（`http://127.0.0.1:3080`）和 token 两部分，**首次加载时用带 token 的地址完成握手**（换取 cookie 存入该主机的分区），之后就正常了。

> ⚠️ **请整段复制，不要手工编辑那串 token**。URL 标准会把 query 里的 `+` 解码成空格 —— 如果 token 里恰好含 `+`，手工抄写极易出错。直接复制粘贴最稳。

> ⚠️ **这个 token 每次 dsh 重启都会变**（进程启动时随机生成，没有配置能让它固定）。
> dsh 重启后如果又报 401，客户端会自动**重放一次**握手；若仍失败，请用**托盘的「添加主机…」**把**新**的带 token 地址重新粘贴一次
> （macOS / Linux 上该入口在菜单栏「编辑(E)」里；Windows 上菜单栏不显示，只有托盘。
> 重新添加同一地址不会丢失已保存的登录态——分区是按 origin 命名的）。

### 3.0 走 SSO 门户的地址：登录后需要手动「重新加载」

如果你的 dsh 地址经过一层登录门户（典型如绿联 UGOS 的容器远程地址
`https://app-3080-<名字>.ugdocker.link/`），会遇到这个现象：

1. 客户端加载该地址 → 被门户 **302** 到登录页；
2. 你登录成功 → 门户跳到**它自己的桌面**，且**不回跳**到原地址；
3. 于是客户端停在门户桌面，**永远到不了 dsh**。

**这不是客户端故障，也不是地址填错** —— 同一个地址在浏览器里"已登录状态下再访问一次"就能直接进 dsh。

**操作**：在客户端窗口里完成登录后，用**托盘「主机列表」→ 该主机 →「重新加载」**（或按 `Ctrl+R`；macOS / Linux 上该入口在菜单栏「主机(H)」里）。
此时客户端会重新请求**配置里的原始地址**（而不是停留在门户桌面），带着刚刚取得的登录态，即可进入 dsh。

> 使用 `webContents.reload()` 是不行的 —— 那只会再加载一次门户桌面。这也是「重新加载」被单独做成一个菜单项、而不是复用「打开」的原因。

> **补充（改 token 之后）**：编辑主机更新了 launch token 后，点「重新加载」也应能进入 dsh。窗口会把最新配置一并接收，401 时用**新的** token 重放一次握手。

### 3.05 链接与窗口行为

点击链接时，客户端按「**这个目标是不是我们已知的站点**」来分流：

| 操作 | 预期 |
|---|---|
| 在门户里点 **dsh 图标**（其地址正是你配置的那台主机） | **当前窗口**变成 dsh（**不**新开窗口） |
| 在 dsh 里点**外部链接**（如 GitHub） | 跳 **系统默认浏览器** |
| 在门户里点**门户自己的页面**（站内跳转） | 在**当前窗口**内跳转，不跳浏览器 |
| 点 `mailto:` 等非网页链接 | 交给系统 |

**判定规则**（只比较 `协议://主机:端口`，路径与参数不参与）：

1. 目标是**你配置的某台主机** → 客户端内打开
2. 目标是**当前页面所在的站点** → 客户端内打开
3. 其余一律 → 系统浏览器

**比较前会规范化**，所以 `https://GitHub.com`、`http://x:80`、`http://x:3080/` 这类写法都能正确识别。

**其他窗口行为**：

| 操作 | 预期 |
|---|---|
| 窗口标题 | 形如 `主机名 — 页面标题`（**带主机名前缀**） |
| 内容窗口（页面自己开的）顶部 | **没有**菜单栏（菜单栏只长在主机窗口上） |
| 在内容窗口按 `Ctrl+W` | 关闭该窗口 |
| 托盘/菜单主机列表 → 某台主机的「**打开**」 | 该主机在**当前窗口**内打开（替换当前窗口） |
| 托盘/菜单主机列表 → 某台主机的「**新窗口打开**」 | 该主机**另开一个窗口**，当前窗口保留（多窗口并行） |

> **「开新窗口」只在菜单里，不在页面链接里**：页面里的链接（含门户里的 dsh 图标）
> 一律在当前窗口打开。想并行看两台主机，用主机列表里的「新窗口打开」——意图是
> **每次显式**给出的。同一台主机永远只有一个窗口（两份 WebSocket 连同一台 dsh
> 既浪费又会让页面状态互相打架），所以对已打开的主机点任一动作都只是唤起它。

> ⚠️ **一个已知的语义取舍**：若某个图标指向的是你**另一台**已配置主机，当前窗口会加载它，但「当前主机」仍是原来那台——此时点菜单的「重新加载」会把你拉回原主机。单主机场景不受影响。

### 3.1 Windows 特有：关窗行为（修复项，重点验证）

**修复前**：Windows 上关掉主机窗口 = 应用直接退出，托盘消失。
**修复后**：关窗应**最小化到托盘**，应用继续驻留。

**验证步骤与预期**：

| 操作 | 预期 |
|---|---|
| 点主机窗口右上角的 ✕ | 窗口消失，但**托盘图标仍在**，应用没退出 |
| 托盘 → 「打开客户端」 | 窗口重新出现并获得焦点（不是新开一个窗口） |
| 托盘 → 「关闭客户端」 | **应用真正退出**，托盘图标消失 |
| 关掉「添加 dsh 主机」欢迎窗口的 ✕ | 该窗口正常关闭（**不**缩到托盘） |

> 若关窗后应用直接没了，说明 W-2 修复未生效，请回报。

## 4. 客户端设置窗口（0.2.0 / 0.2.1 新增，重点验证）

壳自身的行为偏好。这些设置**只作用于客户端**（通知、启动与关窗行为、更新），不影响远端 dsh 本身——dsh 自己的偏好仍由 dsh 网页里的设置面板管。

### 4.0 从哪打开（三个入口都要能通）

| 入口 | 操作 | 预期 |
|---|---|---|
| 托盘 | 托盘 →「**客户端设置**」 | 打开「客户端设置」窗口（560×640） |
| 菜单栏 | 「编辑(E)」→「**设置…**」 | 同上（macOS / Linux；Windows 上菜单栏不显示，见 §3.00） |
| 快捷键 | `Ctrl+,`（macOS 为 `Cmd+,`） | 同上 |

> ⚠️ **`Ctrl+,` 在 Windows 上必须能按出窗口**。这一项是刻意双注册的：既挂在 application menu 上，又在窗口内注册了一份 `before-input-event`——Windows 上主机窗口是无边框的，菜单栏根本不显示，只注册菜单栏的话这个键会**按了毫无反应**。请专门验这一条。
>
> **窗口只允许存在一个**：已经开着时再点入口，应把既有窗口唤到前台（最小化的先还原），**不是**再开第二个。两个窗口同时编辑同一份 `settings.json` 会互相覆盖。

### 4.1 五项偏好 + 版本区（逐项确认存在、可保存）

| 分组 | 设置项 | 默认值 | 预期行为 |
|---|---|---|---|
| 通知 | 弹出系统通知 | **开** | 关掉后，审批请求与新消息都**不再**弹系统通知 |
| 通知 | 消息通知的静默期 | **15 秒**（范围 15–300） | 一轮输出结束后再等这么久仍无新输出才提醒；**审批通知不受它影响**，始终立即弹 |
| 启动与关窗 | 启动时 | **打开上次使用的主机** | 可改为「每次显示『添加主机』页」 |
| 启动与关窗 | 关闭窗口时收进托盘（不退出） | **开** | 关掉则**关窗即退出**客户端 |
| 更新 | 启动后在后台检查新版本 | **开** | 关掉则**整个更新器都不装配**（连「是否重启安装」的询问也不会再有） |
| 更新 | 当前版本 + 「立即检查更新」 | —— | **不是偏好**（不可写、不落盘），是只读信息与一个动作，见 §4.4 |

**五项偏好的默认值全部等于 0.2.0 之前的硬编码行为**——装上升级后，不碰设置的话行为应当与旧版**一模一样**。

> 📌 **0.2.0 发布时有六项，现在是五项**：0.2.5 删掉了「**跨主机跳转时开新窗口**」——那个全局开关回答不了「**这一次**想怎样」，两版都没收敛，已改为在主机列表里**每次显式**选「打开」/「新窗口打开」（见 §5.2）。因此你在设置窗口里**不该**再看到它；旧 `settings.json` 里残留的该字段会被**忽略**，同文件其它字段不受影响（无需迁移）。

> 静默期的输入框请试一次越界：填 `0` 或 `9999`，保存时输入框应被**纠正到 15 / 300**（界面层与主进程各钳一次）。

### 4.2 改完立刻生效（无需重启）

设置窗口**不做**「重启后生效」那套：消费点读的是**当前值**而非启动快照。逐条验：

| 改什么 | 立即验证方式 | 预期 |
|---|---|---|
| 关掉「弹出系统通知」 | 让 agent 停一轮、切走窗口 | 不再弹通知 |
| 把静默期改成 60 秒 | 让 agent 停一轮、切走窗口 | 通知**明显晚于** 15 秒才出现 |
| 关掉「关闭窗口时收进托盘」 | 点主机窗口的 ✕ | **应用直接退出**（与 §3.1 的默认行为相反）——验完请改回开 |
| 「启动时」改为「每次显示『添加主机』页」 | 退出客户端再启动 | 直接停在欢迎页，即使上次有主机 |
| 关掉「启动后在后台检查新版本」 | 重开客户端，等 30 秒以上，看 `update.log` | 不再出现「开始检查更新」（见 §8.1） |

> ⚠️ 「关窗即退出」这一项改完立刻对**已经开着**的窗口生效（宿主行为现取）。若你改完仍收进托盘，说明现取没做到，请回报。

### 4.3 设置存哪、坏了怎么办

设置存在 `%APPDATA%\dsh-remote-client\settings.json`（`%APPDATA%` 即 `app.getPath('userData')`）。

**验证「损坏不静默丢弃」**：
1. 先记下你改过的值；完全退出客户端；
2. 把 `settings.json` 的内容改成一段**不是 JSON** 的文本（例如 `{{{`）；
3. 重新启动客户端 → 打开设置窗口。

**预期**：
- 同目录下出现备份 **`settings.json.corrupt-<时间戳>`**（原文件被改名留证）；
- 设置窗口显示**全部默认值**，客户端能正常使用。

> 📌 **「文件旧了」与「文件坏了」是两种处置，别混淆**：只有**连 JSON 都解析不了**才产生 `corrupt-` 备份。若文件能解析、只是**缺字段**（旧版本写的、比当前版本少几项），一律按**缺哪项补哪项的默认值**处理——**不备份**。把一个能解析的文件改名，会让用户莫名看到一堆 corrupt 文件。
>
> 因此也**不要**期望「把某个字段改成非法值」会产生备份：那种情况是逐字段回退（坏的那一个退回默认，其余原样保留），同样不备份。

### 4.4 设置 → 更新：版本号与「立即检查更新」（0.2.1 新增）

「更新」一节应显示**当前版本号**，并有一个「立即检查更新」按钮。

| 场景 | 操作 | 预期 |
|---|---|---|
| 版本号 | 打开设置窗口看「当前版本」 | 显示**正在运行的版本号**（形如 `0.2.5`，**不带 `v` 前缀**，与安装包文件名、`package.json` 对得上） |
| 打包版点按钮 | 用安装包装的客户端点「立即检查更新」 | 出现「正在检查…」，随后给出结局文案之一（见下表） |
| **开发模式** | `pnpm dev` 下打开设置窗口 | 版本号正常显示；按钮**禁用**，并已说明原因：**「当前未启用更新检查（开发模式下不检查；也可能是你把上面的开关关掉了）。」** |

> ⚠️ **开发模式下按钮必须是「禁用 + 说明原因」，而不是「点了没反应」**——给一个点不动的按钮比不给更糟。这一条在开发模式下**就能验**，不需要安装包。

**结局文案**（五种，逐条对上即可）：

| 结局 | 文案 |
|---|---|
| 已是最新 | 已是最新版本。 |
| 发现新版本 | 发现新版本 **X**，正在后台下载；下载完成后会询问是否重启。 |
| 下载中 | 新版本 **X** 正在下载中，请稍候。 |
| 失败 | 检查更新失败（网络不通或更新源异常）。稍后会再自动检查，不影响使用。 |
| 未启用 | 当前未启用更新检查（开发模式下不检查；也可能是你把上面的开关关掉了）。 |

> ⚠️ **「发现新版本 X」里的 X 必须是新版本，不是当前版本。** 这里出过一次真机缺陷：升级弹窗说 0.2.2 已下载完成，同一页却写「发现新版本 0.2.1」——根因是版本号由**当前运行的**版本冒充（0.2.3 已修）。**验证时请核对你本来在跑的版本与文案里的版本号不是同一个数。**
>
> 版本号取不到时显示「**未知**」。**编造一个版本号比显示未知糟得多**——用户会照着它去找一个不存在的安装包。

## 5. 多主机并行窗口（0.2.0 新增，0.2.5 定稿）

### 5.0 模型：每台主机一个窗口

0.2.0 之前，主机窗口是**同一时刻只有一台**（切换主机会关掉旧窗口）。0.2.0 起窗口改为**按主机 id 索引的注册表**，因此：

| 操作 | 预期 |
|---|---|
| 用「新窗口打开」（见 §3.05）打开第二台主机 | **两台主机各自一个窗口**，同时可见、同时连着 |
| 两台窗口里的登录态 | 互不影响（partition 按 origin 隔离） |

**「当前主机」在 0.2.0 起退化为「最后聚焦的那一台」**——这是一个**有意的降级**（多窗口下本就没有唯一的「当前」）。它决定：菜单里那个 `●` 标记落在谁身上、托盘「重新加载 / 立即重试」瞄准谁。验证方式：点一下窗口 A 再点窗口 B，托盘「主机列表」里的 `●` 应随之移动。

### 5.1 同一台主机至多一个窗口（硬不变量）

**这是一个不变量，不是优化**：同一个 origin 并存两份 WebSocket 连到同一台 dsh，既浪费又会让页面状态互相打架。

| 操作 | 预期 |
|---|---|
| 对**已打开**的主机再点「打开」 | 只是**唤起**既有窗口（不新建） |
| 对**已打开**的主机再点「新窗口打开」 | 同样只是**唤起**既有窗口（不新建、也不并存两个） |

> 因此「对已打开的主机点任一动作都只是唤起它」——这条在 §3.05 已经写过，这里是它在多窗口模型下的形式。

### 5.2 「打开」与「新窗口打开」（0.2.5，重点验证）

0.2.0–0.2.4 曾用一个**全局设置**「跨主机跳转时开新窗口」来决定这件事，两版都没收敛，0.2.5 把它**删除**，改为在菜单里**每次显式选择**。

**前置**：先添加两台主机（第二台可以是不存在的地址），并至少打开其中一台。

| 操作 | 预期 | 不通过说明什么 |
|---|---|---|
| 托盘/菜单 →「主机列表」→ 另一台 →「**打开**」 | 目标主机在**当前窗口内**打开，**当前窗口被替换**（不会多出一个窗口） | `hostOpenEffect` 的 `replace` 分支没走通 |
| 托盘/菜单 →「主机列表」→ 第三台 →「**新窗口打开**」 | **另开一个窗口**，当前窗口**保留** | `keep-open` 分支没走通 |
| 对**已打开**的那台点「打开」或「新窗口打开」 | 只**唤起**它，不新建（见 §5.1） | 不变量被破坏 |
| 菜单里找「跨主机跳转时开新窗口」 | **应当找不到**——该项已在 0.2.5 删除 | 你装的是 0.2.4 或更早 |

> ⚠️ **「打开」会先回到那台主机**：若该窗口的页面已被门户 302 带走（停在门户桌面，见 §3.0），点「打开」会先重新加载到该主机再唤起。**用户点「打开」的意图是回到那台主机**，而不是被唤到一个显示门户的窗口。这一条请专门验一次（门户部署下最容易看出来）。
>
> 📌 **页面里的链接不再受任何开关影响**：门户里点 dsh 快捷方式**恒定在本窗口内打开**（见 §3.05）。「开新窗口」只从菜单里来。

### 5.3 多窗口下需要专门确认的三件事

0.2.0 发布时**多窗口的真实交互尚未真机验证**（该版本 Notes 明确列出），以下几项请重点走一遍：

| # | 验证 | 预期 | 为何要单独验 |
|---|---|---|---|
| 1 | 两台主机同时开着，让**非当前**那台弹出通知 | 通知标题是**发起它的那台**的主机名；点击**回到那一台** | 取「当前主机」会让 B 窗口的通知显示 A 的名字、点了跳到 A |
| 2 | 两台主机在 dsh 里设**不同的皮肤**（深/浅），来回切换焦点 | 各窗口顶部那一条**各自跟随自己的页面** | `nativeTheme` 是**进程级单例**，两个窗口皮肤不同时有互相覆盖的风险——请如实记录实际现象 |
| 3 | 依次关掉**全部**窗口 | 应用**不退出**，托盘仍在，「打开客户端」能唤回 | 多窗口后「全部窗口关闭」的退出判定需要重新确认（托盘可用时本就应当常驻） |

> 第 2 项若出现「后动的窗口把另一个也改了色」，**请务必回报并附截图**——那说明进程级单例确实会串台，是需要排入后续版本的取舍点。

## 6. 壳页面外观与窗口形态（0.2.1 / 0.2.2）

### 6.1 壳页面统一白底（0.2.1 改）

**改之前**这四个页面是深色（`#151517`）。0.2.1 起统一改为**白底**，同时整套配色（文字、边框、次要按钮、警示框、成功/失败色）都换成了浅色可读的值。

| 页面 | 何时会看到 | 预期 |
|---|---|---|
| **welcome**（欢迎页 /「添加主机」） | 首次启动、托盘「添加主机…」 | 白底、深色文字，各输入框与按钮清晰可读 |

### 6.2 设置页顶部必须可达（0.2.3 修）

设置页内容比一屏高时，**最上面一行（「客户端设置」标题与「弹出系统通知」开关）必须能滚到**。

> ⚠️ 这里出过一个真机缺陷：`body` 用了 `height: 100vh` + `place-content: center`，表单比视口高时网格轨道被「居中」到容器外，**上半部分落到负坐标**，滚动条从 0 开始——那一截**用滚动条够不到**（截图里最顶部是「消息通知的静默期」而不是标题）。改成 `min-height` 后正常。
>
> **验证**：把设置窗口拉到最矮，确认能滚到「客户端设置」标题与第一个开关。

### 6.3 Windows 上主机窗口的 DevTools 弹独立窗口（**窗口形态约束，不是缺陷**）

在**主机窗口**按 `Ctrl+Shift+I` 或 `F12`，DevTools 会**弹出一个独立窗口**，而不是在右侧内嵌。

**这是已实测判定的结论，请不要当缺陷报**。同一份代码、同一个 mode 的真机实验结果：

| 窗口 | 边框 | `Ctrl+Shift+I` 的表现 |
|---|---|---|
| 客户端设置（**有**边框） | 有 | **内嵌**（右侧分栏） |
| 主机窗口（Windows，**无**边框） | 无 | **独立窗口** |

**原因**：主机窗口在 Windows 上是**无边框**的（把顶上那一条让给 dsh 自绘，从而跟随应用主题，见 §3）。无边框即「no chrome」，而 DevTools 停靠需要窗口自身的 chrome 布局容器——**与 `mode` 参数无关**。

**这是一个有意的取舍**（用户已明确选择**保留自绘顶部、接受 DevTools 独立**）：唯一能让主机窗口内嵌 DevTools 的办法是去掉无边框，而那会牺牲顶部主题跟随。**macOS / Linux 的主机窗口有边框，DevTools 正常内嵌。**

> 因此这条**不是**待修项。若你在有边框的窗口（设置 / 编辑 / 添加主机）里发现 DevTools 也弹独立窗口，那才是缺陷，请回报。

## 7. 离线与自动重连（修复项，重点验证）

规格要求指数退避重试（1s→2s→4s→8s→…→30s），**此前完全没实现**。

**步骤**：
1. 打开一台已连上的主机；
2. 停掉 dsh-docker：`docker compose stop`（或 `docker stop dsh`）；
3. 观察窗口。

**预期**：
- 窗口切到离线页；
- **窗口标题出现倒计时**（形如「离线，N 秒后重试」，间隔逐次翻倍至 30s 封顶）；
- 托盘图标变**灰色**、tooltip 显示「（离线，正在重试）」；
- 托盘「主机列表」里该主机出现「立即重试」，点它立刻重试（macOS / Linux 上在菜单栏「主机(H)」里）。

**恢复**：`docker compose start`。

**预期**：客户端**自动恢复**到 dsh 界面，无需手动干预。

> ⚠️ 注意：如果 dsh 页面**已经在窗口里渲染过**，容器停了但前端可能仍显示旧界面（WebSocket 断开），而壳的离线页只在页面**加载失败**时触发。**若你看到"界面还在但连不上"而不是离线页，这属于预期行为** —— 请把这个现象告诉我，它决定阶段 2 要不要补「WebSocket 断开也提示离线」。

## 8. 自动更新（差分）—— 升级验收

**这一节验的是「已装的旧版客户端，能不能自己拿到新版」。** 它天然需要两个版本，因此下面一律写成 `<旧版本>` → `<新版本>`——你验的是哪一版就代入哪一版。

> 📌 **本节曾经写死过 `v0.1.7 → v0.1.8`，并标着「需等 v0.1.8 发布后才能执行」。那个前提早已不成立**（当前已发布到 **0.2.5**，自动更新链路从 0.1.7 起就在正常运转）。保留这段说明是为了避免读者再照着旧编号理解——每一步的验收价值不变，变的只是版本号由你代入。

### 8.0 为什么必须发两版

| 角色 | 要求 | 谁来装 |
|---|---|---|
| **`<旧版本>`** | 必须 **≥ 0.1.7**（那版起才带上更新器与 `latest.yml` / `.blockmap`） | 要**手动装一次**（约 106MB） |
| **`<新版本>`** | 任意更大版本号，内容随意（哪怕只改一行） | **不用装** —— 装好的 `<旧版本>` 应当自己发现它 |

所以验收分两段：

- **`<新版本>` 发布前**：`<旧版本>` 只能验证「**不添乱、不影响正常使用**」（见 §8.1）。此时不存在更新的目标版本，什么都不会发生——**这是正确行为，不是缺陷**。
- **`<新版本>` 发布后**：执行 §8.2 的完整链路验收。

> ⚠️ **`<旧版本>` 低于 0.1.7 时，本节整节都不适用**：那些版本里没有更新器，只能手动装安装包，它们不会被自动更新到。这是最后一次手动升级的由来。

### 8.1 任何一版发布前：先确认它不添乱（随时可做）

这四条**不需要第二个版本**就能验，**任何一条不通过都是真缺陷**：

| 操作 | 预期 |
|---|---|
| 正常启动客户端（打包版安装后） | 界面、托盘、主机连接**一切照旧**，与本版之前无差别 |
| 启动后静置 **1 分钟**，全程观察 | **不弹任何窗口/对话框**（包括不提示「已是最新版本」这类废话） |
| **断网启动**（拔网线 / 关 Wi-Fi） | 仍**不弹任何错误框**。只在 `update.log` 里留一行 `检查更新失败（已忽略，不影响使用）…` |
| `pnpm dev` 开发模式启动 | 同样不弹任何东西。更新器**在开发模式下整个不启动**（没有 `app-update.yml`，启动它只会刷错误日志）——这是刻意设计 |
| 设置里的「启动后在后台检查新版本」**关掉**后启动 | 更新器**整个不装配**，`update.log` 里**不出现**「更新器启动」（0.2.0 起；见 §4.1 与 §4.4） |

> **日志去哪看（0.1.7 起有确定答案）**
>
> 更新器会把关键节点写进**用户目录**下的 `update.log`，打包版也能看，不需要命令行：
>
> ```powershell
> Get-Content "$env:APPDATA\dsh-remote-client\update.log" -Tail 20
> ```
>
> 找不到就用这条定位（若目录名不同）：
>
> ```powershell
> Get-ChildItem $env:APPDATA -Recurse -Filter update.log -ErrorAction SilentlyContinue |
>   Select-Object FullName
> ```
>
> 日志长这样（每行一个 ISO 时间戳）。**下面这段是 0.1.7 时代的历史样本**，仅用于说明格式；你自己的日志里版本号与时间戳当然不同：
>
> ```
> 2026-10-11T02:31:07.512Z 更新器启动（当前版本 0.1.7，日志位于 update.log）
> 2026-10-11T02:31:37.480Z 开始检查更新（当前版本 0.1.7）
> ```
>
> 0.1.8 起「没找到新版本」也会留一行「检查完成：当前已是最新版本」，因此**「确实没有新版」与「静默失败了」可以区分开**（0.1.7 上没有这一行）。
>
> 它最多保留最近 200 行（每条截断到 400 字符），所以**不会无限增长**，可以一直留着。
>
> 加这条日志之前这里写的是「用命令行启动 exe，或开 DevTools 看 Console」——那对最终用户
> 基本不可行，等于「更新在真机上为什么没反应」无据可查。现在 `update.log` 是那条依据。

### 8.2 `<新版本>` 发布后：完整链路验收（本节是重点）

**前置**：`<新版本>` 已作为 tag 发布到 Release，且 Release 里**三样齐全**——`setup.exe`、`latest.yml`、`*.exe.blockmap`（见 README「Release 里的三个文件」）。

按顺序执行，**每一步都要看结果**（下表里的 `0.1.7`/`0.1.8` 是原始示例，请替换为你实际用的 `<旧版本>`/`<新版本>`）：

| # | 操作 | 预期 | 不通过说明什么 |
|---|---|---|---|
| 1 | 确认当前装的是 **`<旧版本>`**，然后启动客户端，静置约 **30 秒** | `update.log` 里出现「开始检查更新」（见 §8.1 的日志查看方法） | 定时器没跑起来 |
| 2 | 保持启动，等待后台下载完成 | 弹出对话框：「新版本 **`<新版本>`** 已下载完成，现在重启安装吗？」，按钮为「立即重启」/「稍后」 | 静默期/策略把提示吞了 |
| 3 | **记录实际下载量**（见下方说明） | 明显小于 106MB | 差分没生效，退化成整包重下 |
| 4 | 点 **「立即重启」** | 应用**确实退出**，短暂安装后**自动重新打开**，且版本号变为 **`<新版本>`** | ⚠️ 见下方「已知陷阱」 |
| 5 | 重启后确认版本 | 设置窗口「当前版本」（§4.4）/ 窗口标题 / `package.json` 对应版本均为 `<新版本>` | 安装未真正完成 |
| 6 | **另起一轮**：先点「稍后」，不做任何操作 | 对话框关闭，**无任何副作用**（窗口、托盘、主机连接一切照旧） | 更新影响了主链路 |
| 7 | 承上，**完全退出客户端再启动**，再等一轮检查 | **不再就 `<新版本>` 弹第二次**（用户已经表过态了） | 状态没记住，用户会被反复打扰 |
| 8 | 再发一个更高的 **`<更新版本>`**（若愿意配合测） | 会**重新**就 `<更新版本>` 提示 | 状态记住了但换版本后没重置 |
| 9 | 在设置里点「**立即检查更新**」（§4.4） | 文案里的版本号与第 2 步弹窗的**是同一个**新版本号 | 用当前版本冒充新版本了（0.2.3 修过） |

**第 3 步怎么记下载量**：差分是否真的生效，唯一判据就是实际下载了多少。
最直接的方式是在下载期间用系统资源监视器（Windows 任务管理器 →「性能」→「以太网」）
观察该进程的接收流量；若从命令行启动，也可直接看更新器输出——**0.1.9 起库的内部日志也接进了 `update.log`**（前缀 `[库]` / `[库·警告]` / `[库·错误]`），差分失败回退整包会明确打出来。
**把数字记下来**——它决定「差分」这件事到底值不值得保留。

**参考数字**：0.1.9 → 0.1.10 的真机实测是「完整包 106.3MB，实际只下 **1.26MB**（约 1%）」。你的数字应当在同一量级；若接近 106MB，就是差分没生效。

**第 4 步为什么是本节最关键的一条**：

> ⚠️ **已知陷阱（0.1.7 发布前后已修复，见提交 `11239d3`）：由 `quitAndInstall()` 发起的退出，Electron 的 `before-quit` 是在所有窗口 `close` **之后**才 emit 的——与普通 `app.quit()` 的顺序**相反**。**
>
> 而本应用的主机窗口 `close` 被拦截为「隐藏到托盘」，只有 `quitting === true` 才放行。于是若等到 `before-quit` 才置位，`close` 到达拦截点时它还是 `false` → `preventDefault()` → **Electron 取消整个退出流程**。症状正是「点了立即重启，窗口消失了但版本没变」，且**必然发生、不是偶发**。
>
> 修法是在用户确认后、调用 `quitAndInstall()` **之前**就置位 `quitting`（记在 `UpdaterDeps.promptRestart` 的契约里，`src/main/updater.ts` 与 `src/main/index.ts` 都有注释）。
>
> **给将来改动这个功能的人**：这条路径只在「打包版 + 真的下载完更新」时才走到，**单测与产物断言都够不着**。如果你动了退出流程、窗口 `close` 拦截或对话框架构，必须回来重跑第 4 步。改动时请一并读 `src/main/updater.ts` 里 `handleDownloaded` 的注释。
>
> 📌 **注意不要把这个缺陷误记成「注册顺序」问题。** 曾有一版设计文档写成「确认 `before-quit` 早于更新器注册」——那是个**问错了的问题**：注册顺序本来就是对的（`before-quit` 在模块顶层注册，`installUpdater` 在 `boot()` 里才执行），照那条去查**永远查不出问题**。真正的变量是**事件触发顺序**，对应的验收就是第 4 步。

## 9. 局域网 / 远程访问（可选，进阶）

要用**局域网 IP 或域名**（不是 127.0.0.1）时：

### 9.1 trust fence（否则页面能开但 `/api` 全 403）

在 dsh-docker 的 `.env` 里配：
```
DSH_TRUSTED_HOSTS=192.168.1.5:3080
```
或装认证插件：
```bash
docker exec dsh dsh plugin --profile web add @xgone/dsh-remote
docker restart dsh
```

### 9.2 安全上下文（否则剪贴板失效）

壳会对**已配置的 `http://` origin** 设置 `unsafely-treat-insecure-origin-as-secure`，但**该开关只能在启动时生效**。

首次添加 `http://192.168.x.x:3080` 后，欢迎页会显示黄色提示并给**「立即重启」按钮** —— 按下它，该 origin 才会被纳入开关列表。

> 已知 UX 小瑕疵：同一会话内**重复添加同一台 http 主机**仍会再提示一次（语义上正确——它确实仍未生效，但显得啰嗦）。

### 9.3 验证隔离性

同时添加一个 `http://` 和一个 `https://` 主机，确认登录态互不干扰。

## 10. 已知限制（避免误判为缺陷）

以下是**设计上已知**的，不是 bug：

- **原生通知**：**审批通知与消息通知均已真机验证可用**（审批的选择器取自 dsh 上游组件源码 `dsh-client-ui-approval`，不必依赖真机勘察；消息通知在 **0.1.2** 真机确认——窗口失焦时 agent 每回复完一次弹一条）。
  - **审批通知无条件弹**（agent 卡在那里等你）。
  - **消息通知只在窗口失焦时弹**，且要等这一轮**真的安静下来**（最后一轮流式输出结束后，静默期内没有新输出——时长可调，默认 15 秒，见 §4.1）。验证时需先**切走窗口**。中途停下等工具结果不会提醒。
  - **已知的误报边界**：dsh 没有暴露「整个会话是否在跑」的信号，所以若某一步的输出间隙超过静默期，仍可能中途弹一次。**宁可偶尔多弹也不漏报**——漏报的后果是用户干别的去了、永远等不到「干完了」的提醒。
- **`http://` 主机换 IP 或换域名 = 新主机**，需重新登录。这是 dsh 的 cookie 名绑定 authority（`sha256(authority)`）导致的。
- **多台主机可同时开着（每台一个窗口），但同一台主机至多一个窗口**。0.2.0 起窗口改为按主机 id 索引的注册表，切换主机**不再**关掉旧窗口；对**已打开**的主机点「打开」或「新窗口打开」都只是**唤起**它，不会并存第二个窗口（同一个 origin 两份 WebSocket 既浪费又会让页面状态互相打架）。详见 §5。
- **「当前主机」= 最后聚焦的那一台**（0.2.0 起的**有意降级**）：多窗口下本就没有唯一的「当前」，菜单里的 `●` 标记与托盘的「重新加载 / 立即重试」都以它为目标。因此点过另一个窗口之后，`●` 会跟着挪过去——这是预期，不是漂移。
- **`nativeTheme` 是进程级单例**：两台主机的窗口若各自设了**不同的皮肤**，最上面那一条的表现需要真机确认（见 §5.3 第 2 项）。这是待观察项，不是已定论的行为。
- **macOS 上内容窗口仍会显示菜单栏**：Windows/Linux 上已按窗口移除；macOS 的菜单属于**应用级**，按窗口移除会连带影响主机窗口的菜单，得不偿失。**仅影响 macOS**。
- **页面若依赖 `window.open` 的返回值会报错**：为了让链接在**当前窗口**打开，我们必须拒绝 Electron 默认的"开新窗口"行为，于是 `window.open()` 返回 `null`。页面若接着用这个返回值（如 `w.focus()`）会抛一个 JS 错误——影响仅限该页面自身，**导航已由我们完成**。
- **链接分流的一个取舍**：见 §3.05 —— 图标若指向**另一台**已配置主机，当前窗口会加载它，但「当前主机」不变。
- **未签名应用**：若你日后打包成 exe，Windows Defender / SmartScreen 可能警告；直接用 `pnpm dev` 开发模式跑不涉及。
- **自动更新只在打包版生效**：`pnpm dev` 下更新器整个不启动（没有 `app-update.yml`，启动它只会刷错误日志）；设置里关掉「启动后在后台检查新版本」也是同样效果。**因此不能靠开发模式验证任何更新行为**，必须用安装包（见 §8）。设置页的「立即检查更新」按钮在这种情形下会**禁用并说明原因**（§4.4）。
- **自动更新的一切失败都是静默的**：断网、更新源不可达、`latest.yml` 解析失败，都只在 `update.log` 里留一行，**不弹任何框**。这是刻意的（用户没在等更新，弹框打扰是负收益）——所以**「什么都没发生」通常就是正确行为**，别急着当缺陷报。要判断它到底有没有在跑，看 `update.log`（§8.1 有查看方法）：它会区分「确实没有新版」与「静默失败了」，这正是加这条日志的目的。
- **只提示一次不是健忘**：同一版本问过用户之后不再重复问（状态存在 `userData/update-state.json`）。若你想重新看到对话框，删掉该文件即可。
- **0.1.6 及更早的版本不会自动更新**：那些版本里没有更新器。它们必须**手动装一次 0.1.7**，之后才进入自动更新链路。
- **卸载会保留 `update-state.json` 与 `settings.json`**：与其他用户数据一并保留（卸载时不清 `userData`）。重装后「已提示过的版本」与客户端设置都沿用，这是刻意的。
- **Windows 上主机窗口的 DevTools 会弹独立窗口**：这是**窗口形态的约束，不是缺陷**，详见 §6.3。**不要试图去修**——唯一的办法是去掉无边框，而那会牺牲用户已明确要保留的顶部主题跟随。

## 12. 自动化部分先跑一遍（可与 GUI 验证并行）

GUI 验证前先确认自动化部分是绿的：

```powershell
pnpm test        # 构建 + 全部测试（含构建产物断言）
pnpm typecheck
```

预期：`Tests passed`、typecheck 退出码 0、`out\` 下有**恰好 9 个**产物文件：

```
main/index.js
preload/host.cjs
preload/welcome.cjs
preload/edit.cjs
preload/settings.cjs
renderer/offline.html
renderer/welcome.html
renderer/edit.html
renderer/settings.html
```

> ⚠️ **是 9 个，不是 5 个**。产物断言同时做**正向**（这九个都在）与**反向**（总数恰好等于九个）两侧检查，因此多出一个文件（例如意外生成的共享 chunk）也会被挡住。
>
> `settings.*` 两个产物是 **0.2.0** 加入的（客户端设置窗口）。它们曾**漏登** `electron.vite.config.ts` 的显式入口列表——那份配置用显式列表而非 glob，构建会**安静跳过**未登记项，于是出现过「402 项测试全绿 + typecheck 退出码 0，而这两个产物根本没被构建出来」。产物断言从「七个」改为「九个」，并新增了一条守根因的断言：「每个 renderer 页面与 preload 都登记进了构建入口」。
>
> 本指南早期版本这里写的是「恰好 5 个」，那是 0.1.x 时代的数字。

这条命令在阶段 1 抓出了两个 P0（`out/renderer/` 不生成、preload 内联 electron 包），**它们单测和类型检查都抓不到** —— 所以若发现构建相关异常，`pnpm test` 是第一道筛子。
