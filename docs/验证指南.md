# 图形环境验证指南（阶段 1）

本指南用于在**有图形界面的机器**上验证 dsh-remote-client 阶段 1。

本开发环境无 GUI，因此以下内容**从未被运行验证过**：窗口能否打开、能否连通真实 dsh、托盘外观、登录态持久化、离线重连的实际行为。这份指南就是为把这些验证出来而写的。

---

## 0. 准备：把代码弄到验证机器

仓库体积仅 **61K**（不含 `node_modules`），直接拷贝即可：

```bash
# 在开发机（本环境）
tar czf /tmp/dsh-remote-client.tar.gz \
  --exclude=node_modules --exclude=.git --exclude=out --exclude=.tmp \
  -C /workspace/code dsh-remote-client

# 拷到验证机后
tar xzf dsh-remote-client.tar.gz && cd dsh-remote-client
```

> 该仓库目前**没有配置 git remote**。若你希望后续以 git 方式协作，请给它加一个远程仓库再 push。

**环境要求**：Node ≥ 20、pnpm。electron 会下载约 100MB 的二进制（开发环境当时用 `ELECTRON_SKIP_BINARY_DOWNLOAD=1` 跳过了，验证机上需要真实下载）。

```bash
pnpm install
```

## 1. 关键起点：优先用 `127.0.0.1` 验证，可零配置

**如果你的 dsh-docker 就跑在验证机本机**，直接用 `http://127.0.0.1:3080` 添加主机——这是最省事的路径，能一次绕开两个坑：

| 坑 | 用 127.0.0.1 时 |
|---|---|
| dsh 的 trust fence 拒绝非 loopback Host（表现为页面能开但 `/api` 403） | `127.0.0.1` 是 loopback，**直接放行**，无需 `DSH_TRUSTED_HOSTS`，也无需装 `dsh-remote` |
| 明文 HTTP 不是安全上下文（`navigator.clipboard` 失效） | `127.0.0.1` 属于浏览器认定的 potentially trustworthy origin，**是安全上下文**，剪贴板正常 |

只有当你需要用**局域网 IP 或域名**访问时，才需要处理这两件事（见 §5）。

---

## 2. 起步：最小闭环（先只验证它能跑起来）

这是**最高优先级**的一步——阶段 1 修的两个 P0 缺陷都出在这条路径上，必须最先确认。

```bash
pnpm dev
```

**预期**：出现一个标题为「添加 dsh 主机」的窗口（560×420），含地址、显示名两个输入框和「添加并打开」按钮。

**这一步验证的是**：
- `out/renderer/welcome.html` 能被加载（P0：此前 `out/renderer/` 根本不生成 → 白屏）
- 欢迎页的 preload 能加载（P0：此前 preload 内联了整个 npm electron 包 → `window.shell` 为 undefined）

**如果白屏**：按 `Ctrl+Shift+I`（macOS `Cmd+Opt+I`）开 DevTools 看 Console。开发模式下 `pnpm dev` 也会在终端打印主进程错误。把 Console 的报错原文记下来（见 §7 回报模板）。

**如果窗口开了但按钮点了没反应**：在 DevTools Console 执行 `window.shell`，若为 `undefined` 就是 preload 加载失败，把主进程终端的报错发我。

## 3. 核心验证：连上一台真实 dsh

在欢迎页填入地址并提交。

**预期（按顺序）**：
1. 提交后立即打开一个主机窗口，标题先是主机显示名；
2. 页面加载远端 dsh 的界面——**若远端在线**，出现 dsh 的会话列表或登录页（取决于是否装了 `dsh-remote`）；
3. 若远端不可达，显示壳自有的离线页，并给出失败原因 + `DSH_TRUSTED_HOSTS` 提示。

**然后逐项确认**：

| 项 | 操作 | 预期 |
|---|---|---|
| 登录态持久化 | 登录 → 完全退出客户端（不是关窗口，是退出应用）→ 重新 `pnpm dev` | 直接进入已登录状态，不再要求登录 |
| 多主机隔离 | 添加第二台主机（可用一个不存在的地址）→ 切回第一台 | 两台的登录态互不影响 |
| 托盘 | 查看系统托盘/菜单栏 | 有 dsh-remote-client 图标；菜单列出两台主机，当前主机前带 `●`；含「添加主机…」「退出」 |
| 主机切换 | 托盘菜单点另一台 | 窗口切换到该主机；菜单 `●` 跟着变 |
| 重置登录态 | 对某台点「重置登录态」→ 重开该主机 | 回到登录页 |
| 删除 | 删除一台 | 菜单不再列出；**删光全部后菜单仍有「添加主机…」**（这是修复项，此前删光就再也加不回来） |
| 拖拽上传 | 拖一个本地文件进 dsh 窗口 | 作为附件进入远端工作区（**前端自带此能力，壳未做任何处理**） |

## 4. 离线与自动重连（修复项，重点验证）

规格要求指数退避重试（1s→2s→4s→8s→…→30s），**此前完全没实现**。

**步骤**：
1. 打开一台已连上的主机；
2. **停掉 dsh-docker**（`docker compose stop` 或 `docker stop dsh`）；
3. 观察窗口。

**预期**：
- 窗口切到离线页；
- **窗口标题出现倒计时**（形如「离线，N 秒后重试」，间隔逐次翻倍直到 30s 封顶）；
- 托盘 tooltip 出现「（离线，正在重试）」，菜单项标注「（离线）」；
- 菜单里有「立即重试」项，点它立刻发起重试。

**恢复**：重新启动容器。

**预期**：客户端**自动恢复**到 dsh 界面，无需手动干预；恢复后标题不再被倒计时覆盖。

> ⚠️ 注意：如果容器停了但 dsh 页面**已经在窗口里渲染过**，前端自身可能仍显示旧界面（WebSocket 断开）。壳的离线页只在 `did-fail-load`（页面加载失败）时触发。**如果你看到的是"界面还在但连不上"而不是离线页，这属于预期行为**，请把这个现象告诉我——它关系到阶段 2 是否要补"WebSocket 断开时也提示离线"。

## 5. 局域网 / 远程访问（可选，进阶）

如果要用 **局域网 IP 或域名**（不是 127.0.0.1），需要处理两件事：

**5.1 trust fence**（否则页面能开但 `/api` 全部 403）

在 dsh-docker 的 `.env` 里配：
```
DSH_TRUSTED_HOSTS=192.168.1.5:3080
```
或安装认证插件：
```bash
docker exec dsh dsh plugin --profile web add @xgone/dsh-remote
docker restart dsh
```

**5.2 安全上下文**（否则 `navigator.clipboard` 失效）

壳会对**已配置的 `http://` origin** 设置 `unsafely-treat-insecure-origin-as-secure`，但**该开关只能在启动时生效**。

所以你首次添加一个 `http://192.168.x.x:3080` 主机后：
- 该主机窗口能正常工作，但**复制按钮可能不可用**；
- 欢迎页会显示一条黄色提示，说明需要重启客户端才能让该 origin 生效，并提供**「立即重启」按钮**。

**请按下「立即重启」**（或手动退出重开），重启后该 origin 被纳入开关列表，剪贴板等功能即恢复正常。

> 该提示的判定逻辑：只有**明文 `http://`** 且**不在启动时生效列表**中的 origin 才提示；`https://` 与启动时已存在的主机不会提示。
> 已知的 UX 小瑕疵：在同一会话内**重复添加同一台 http 主机**，仍会再次提示（语义上正确——它确实仍未生效，但可能显得啰嗦）。

**5.3 验证隔离性**：同时添加一个 `http://` 主机和一个 `https://` 主机，确认两者登录态互不干扰。

## 6. 已知限制（避免误判为缺陷）

以下是**设计上已知**的，不是 bug：

- **托盘图标是空图占位**（`nativeImage.createEmpty()`），可能完全不可见或只是个占位方块。「离线时图标变灰」因此无法实现，已降级为 tooltip + 菜单标注。
- **没有原生通知**（审批请求/任务完成不会弹系统通知），属于阶段 2。
- **不能重命名主机**，属于阶段 2（添加时可填显示名）。
- **`http://` 主机换 IP 或换域名 = 新主机**，需要重新登录。这是 dsh 的 cookie 名绑定 authority（`sha256(authority)`）导致的，无法回避。
- **只保留一个主机窗口**：切换主机会关掉旧窗口，避免并存两份 WebSocket。
- **`out/` 目录**若被删，`pnpm test` 会失败并提示"请先运行 pnpm build"——这是故意的（构建产物断言测试）。

## 7. 出问题时的回报模板

请按这个格式回报，能大幅加快定位：

```
【步骤】§3 登录态持久化
【操作】登录 → 退出应用 → 重新 pnpm dev
【预期】直接进入已登录状态
【实际】仍要求登录
【证据】
  - 主进程终端输出：<粘贴>
  - DevTools Console 报错：<粘贴>
  - 截图/录屏：<如有>
【环境】macOS 14 / Node 20.11 / pnpm 9；远端 = 本机 docker
```

**特别有价值的三个信息**：
1. 主进程终端的完整报错（`pnpm dev` 的输出）
2. DevTools Console 的报错原文（`Ctrl+Shift+I`）
3. 窗口标题栏的实际文字（用于判断倒计时与标题逻辑是否正常）

## 8. 自动化部分的回归（可与 GUI 验证并行跑）

GUI 验证前，先确认自动化部分是绿的：

```bash
pnpm install
pnpm test        # 构建 + 全部测试（51 项，含构建产物断言）
pnpm typecheck
```

预期：`Tests 51 passed (51)`、typecheck 退出码 0、`out/` 下有恰好 5 个产物文件。

这条命令在阶段 1 抓出了两个 P0（`out/renderer/` 不生成、preload 内联 electron 包），**它们单测和类型检查都抓不到**——所以验证时若发现构建相关异常，`pnpm test` 是第一道筛子。
